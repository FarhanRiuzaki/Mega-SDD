**Date:** 2026-05-24
**Auditor:** claude (general-purpose agent, sonnet-4-6)

**Scope:** Forensic read-only audit — 10 focus areas post-Iter-28 (multi-scope PRD picker)

## Summary

Iter 28 delivered a working multi-scope PRD picker for the `generate-intent` phase. The picker algorithm, memory schema, vault-contract schema, handoff-contract schema, scenario fixtures, and trigger tests are all present and internally consistent. The front-end of the pipeline is sound.

However, scope information is not propagated to any downstream skill. Every skill from `bind-codebase` through `emit-agents-md` is completely unaware of the `scope`, `scope_metadata`, and `prd_sha256` fields added to `vault.json` in Iter 28. A user who runs `--auto`, picks scope=BE, and executes the full pipeline will produce a vault tagged BE — but every artifact downstream (binding, units, bolt reports, AGENTS.md) will contain no scope context. The handoff YAML block was updated but no consuming skill reads it.

Additional structural issues: Step 0.9 (scope detection) is placed in the file before Step 0.8 (scan-aware loading), contradicting the stated execution order. The three new Iter 28 halt types are absent from `orchestrate-flow`'s halt taxonomy. One spec claim in `vault-contract.md` (diff-vault reads `prd_sha256`) is unimplemented.

**Overall health: YELLOW.** Iter 28 is functionally safe (no anti-halu rails broken, no hard-gate bypassed), but the scope surface is incomplete. The picker fires and tags vault.json; the scope tag goes no further.

#### P1-1: Step 0.9 placed before scan-aware loading in generate-intent SKILL.md (execution order inversion)

**File:** `skills/generate-intent/SKILL.md`
**Lines:** Step 0.9 section header at line 379; scan-aware context loading section at line 557 (labelled "Scan-aware context loading (v1.8+, Iter 16)").

Step 0.9 (scope detection + PRD filtering) appears physically 178 lines before scan-aware context loading in the file. Yet Step 0.9's own procedure text (line 381) states:

> "Per `references/scope-picker.md`. Runs AFTER all Step 0.x metadata config (PRD_STATUS, OUTPUT_MODE, squad partition, scan-aware)"

The scope picker is supposed to run after scan-aware loading, but the file places it before. The step numbering table at lines 189-192 lists the known 0.x steps but was not updated to include Step 0.9 in final execution order.

Structural file order found:
```
Step 0   (line ~216) — Output path setup
Step 0.5 (line ~257) — Implementation mode
Step 0.6 (line ~289) — PRD_STATUS
Step 0.7 (line ~315) — OUTPUT_MODE
Squad partition (line 340)
Step 0.9 (line 379)  ← SCOPE PICKER — placed here
Steps 1, 2, 3 ...
Scan-aware context loading (line 557)  ← should be before Step 0.9
```

An AI agent reading the file top-to-bottom will execute scope filtering before scan context is loaded, which is contrary to the spec intent. The scope picker is supposed to know whether a `--scan` map is present when filtering the PRD.

**Required fix:** Move the Step 0.9 section to appear after the scan-aware context loading section (currently at line 557) in the file. Alternatively, add an explicit ordering note in Step 0.9's preamble cross-referencing the scan-aware section with a "do not proceed here until scan context is loaded" guard.

#### P1-2: bind-codebase has zero vault-scope awareness

**File:** `skills/bind-codebase/SKILL.md` (v1.9.2)
**Evidence:** 0 occurrences of `scope`, `scope_metadata`, or `prd_sha256` in the skill (excluding one unrelated match about cross-project memory patterns).

`bind-codebase` reads `vault.json` to perform file/module binding. When a multi-scope vault is present, the binding should be constrained to the chosen scope's modules. Currently, `bind-codebase` has no awareness that the vault was scope-filtered. It will attempt to bind the entire vault.json against the codebase with no scope context.

Additionally, the handoff YAML envelope emitted by `bind-codebase` does not carry a `scope:` field forward. `orchestrate-flow/references/handoff-contract.md` line 44 defines `scope:` as a required v3.20+ envelope block ("v3.20+ — propagates multi-scope PRD picker"), with subfields `id`, `name`, `sibling_scopes`, and `prd_sha256` that downstream skills rely on. `bind-codebase` currently produces handoff envelopes with no `scope:` block — a direct violation of the v3.20 contract.

**Required fix:** `bind-codebase` must read `scope` from vault.json and (a) constrain binding to scope-tagged modules, (b) populate the `scope:` block in its handoff YAML output per handoff-contract.md §v3.20+.

#### P1-3: generate-units does not propagate scope into unit frontmatter

**File:** `skills/generate-units/SKILL.md` (v2.5.3)
**Evidence:** 0 occurrences of `scope`, `scope_metadata`, or `prd_sha256`.

Units are the handoff contract between architect and developer AI. When a vault is scope-tagged (e.g., scope=BE), every generated unit should carry a `scope:` field in its frontmatter so that bolt-executing agents can verify they are operating in the correct scope context. Currently, no scope field is written to unit frontmatter.

This gap means multi-scope projects cannot route units to scope-specific agent squads — the units carry no signal about which scope they belong to. Furthermore, `generate-units` does not populate `scope:` in its handoff YAML, violating the `handoff-contract.md` v3.20+ envelope contract (line 44: `scope:` block required with `id`, `name`, `sibling_scopes`, `prd_sha256`).

**Required fix:** `generate-units` must read `scope` from vault.json and (a) write `scope: <id>` into each unit's frontmatter, (b) populate the `scope:` block in its handoff YAML output.

#### P1-4: emit-agents-md and agents-md-schema.md have zero scope awareness

**Files:**
- `skills/emit-agents-md/SKILL.md` (v1.2.3) — 0 occurrences of `scope` or `scope_metadata`
- `skills/emit-agents-md/references/agents-md-schema.md` — 0 occurrences of `scope` or `scope_metadata`

The AGENTS.md file is the tool-agnostic interop export (Linux Foundation AAIF standard) used by external agents and CI pipelines to understand the project state. When a vault is scope-tagged, the exported AGENTS.md should declare the active scope so consuming tools know which slice of the system they are operating on.

Currently, AGENTS.md exports carry no scope field. A BE-scoped vault and an FE-scoped vault would produce AGENTS.md files indistinguishable at the metadata level. `emit-agents-md` also does not populate the `scope:` block in its handoff YAML (violating handoff-contract.md line 44, same as P1-2/P1-3).

**Required fix:** Add `scope:` field to the AGENTS.md schema in `agents-md-schema.md`, update `emit-agents-md` to populate it from vault.json, and add the `scope:` handoff envelope block to emit-agents-md's output.

#### P1-5: diff-vault spec claim unimplemented — prd_sha256 read not in SKILL.md

**File:** `skills/generate-intent/references/vault-contract.md` line 487 states:

> "diff-vault reads `prd_sha256` to detect PRD changes; pre-v1.12 vaults skip this check gracefully"

**File:** `skills/diff-vault/SKILL.md` (v1.2.1) — 0 occurrences of `prd_sha256`, `scope_metadata`, or `Multi-scope`.

The vault-contract.md was updated in Iter 28 to define `prd_sha256` as a vault.json field. It explicitly documents that `diff-vault` will use this hash to detect PRD drift. That behavior is absent from the `diff-vault` SKILL.md procedure. An AI agent running `diff-vault` will not attempt to read or compare `prd_sha256` because the skill has no instruction to do so.

**Required fix:** Either implement the `prd_sha256` check in `diff-vault` SKILL.md and bump its version, or remove the unimplemented claim from `vault-contract.md`. Leaving a documented behavior that is not implemented is an anti-hallucination rail violation (the spec says one thing, the skill does another).

#### P1-6: Three Iter 28 halt types absent from orchestrate-flow halt taxonomy

**File:** `skills/orchestrate-flow/SKILL.md` (v2.4.0), lines 209-220 (halt taxonomy table)
**File:** `skills/orchestrate-flow/references/routing-rules.md`

The three halts introduced by Iter 28 are:
- `scope_not_declared_in_prd`
- `prd_no_scopes_block_user_rejected_retrofit`
- `prd_retrofit_low_confidence`

Neither `orchestrate-flow/SKILL.md` nor `routing-rules.md` contain any of these halt names (grep confirmed 0 matches in both files). The halt taxonomy table classifies halts as either "always stop chain" or "convergence-eligible (auto-loop)." The three new halts belong in the "always stop" category (they require human input — scope selection or retrofit acceptance). Without taxonomy entries, `orchestrate-flow` in `--auto` mode has no defined behavior when `generate-intent` fires one of these halts: it may swallow it, re-loop incorrectly, or surface it without proper chain-stop semantics.

**Required fix:** Add all three Iter 28 halt types to `orchestrate-flow/SKILL.md`'s halt taxonomy as "always stop chain" entries. Update `routing-rules.md` accordingly. Bump `orchestrate-flow` version.

#### P2-3: Squad partition fires before scope detection in generate-intent file order

**File:** `skills/generate-intent/SKILL.md`
**Lines:** Squad partition section at line 340; Step 0.9 scope detection at line 379.

CHANGELOG Iter 28 claims the new hierarchy is "scope > squad > module > unit." However, in the file, squad partition (line 340) precedes scope detection (line 379). Squad partitioning should be aware of the chosen scope (e.g., a BE-scoped vault should only partition squads within the BE scope), but it fires first.

This is related to P1-1 (step ordering) but is a separate logical concern: even if Step 0.9 is moved to after Step 0.8, squad partition still fires before scope is resolved.

**Required fix:** Squad partition logic should either (a) run after Step 0.9 so it can filter squads by scope, or (b) explicitly document that it partitions the full PRD and scope filtering is applied as a post-pass.

### Advisory (Non-blocking observations)

#### ADV-1: sample-prd-single-scope.md has a YAML comment inside frontmatter

**File:** `tests/scenarios/sample-prd-single-scope.md` line 12

A `# Single-scope: only...` comment line appears inside the YAML frontmatter block. YAML 1.2 supports inline comments, so this is not a parse error. However, some YAML parsers used in older tooling treat `#` lines inside frontmatter as parse failures. This is a cosmetic issue but worth noting for portability.

**Suggested fix:** Move the comment to a markdown line below the closing `---` of frontmatter, or keep it and add a note in the fixture header that YAML 1.2 is required.
