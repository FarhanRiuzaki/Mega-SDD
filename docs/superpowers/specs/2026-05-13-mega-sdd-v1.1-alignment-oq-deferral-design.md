## 1. Context & Motivation

### 1.1 Audit verdict

A 1:1 truthfulness audit of the v1.0.1 README against the actual skill source (`plugins/mega-sdd/skills/*/SKILL.md` + `references/` + `commands/*.md`) returned **MAJOR_DEFECTS** verdict with 8 distinct findings across 7 dimensions. Defects fell into three categories:

- **README hallucinations** (claims with no skill backing) — 5 of the 6 halt protocol types listed; `--chain` flag; `update-plugin` listed as skill
- **Path/naming inconsistencies between skills** — vault default path, `bound-vault/` naming, DRIFT.md vs DRIFT-REPORT.md
- **Skill behavior gaps surfaced by README intent** — `--binding` mode unwritten in resolve-oq; intent-phase resolve-oq gate hidden from diagrams despite routing-rules.md encoding it; source-code OQ deferral mentioned in user model but unformalized in any skill

### 1.2 User-flagged concern (the trigger)

Direct quote from the user reviewing v1.0.1 README:

> "resolve oq kenapa di readme itu setelah detect drift after commit ya? harusnya itu ada di intent.. jadi sebelum masuk ke vault harus clear dlu, kecuali terkait source code"

Translated: "Why is resolve-oq positioned after detect-drift (post-commit) in the README? It should be in intent phase — OQs must be cleared before passing the vault forward, EXCEPT for source-code-related ones."

This concern revealed two distinct gaps:
1. **Visualization gap** — README diagrams don't show the intent-phase resolve-oq gate that's encoded in `routing-rules.md`
2. **Behavior gap** — no skill formalizes the "source-code OQ defers to binding phase" semantic; architect can't currently mark an OQ as code-dependent

### 1.3 The design intent

v1.1.0 closes both gaps:
- **Documentation truthfulness** — README rewritten to match what skills actually do (Fase 1 + 2)
- **Behavior extension** — resolve-oq gains `--binding` mode procedure + 4-action menu including "Defer to binding" + binding phase auto-resolution of deferred OQs (Fase 3)
- **Schema extension** — halt protocol grows from 3 to 8 structured types so prose halts in bind/units/execute-bolts become inspectable (Fase 3 #13)

### 4.2 vault.json OQ schema extension

**Current OQ shape (assumed):**

```yaml
oqs:
  - id: OQ-DATA-001
    priority: P1 | P2 | P3
    section: 03-data-model.md
    text: "Does the user table have a deleted_at column?"
    # implicit: unresolved
```

**New OQ shape:**

```yaml
oqs:
  - id: OQ-DATA-001
    priority: P1
    section: 03-data-model.md
    text: "Does the user table have a deleted_at column?"
    status: pending | resolved | deferred | out-of-scope    # NEW
    # Resolved status:
    resolved_at: <ISO>          # NEW (status=resolved)
    resolution: <answer text>   # NEW (status=resolved)
    # Deferred status:
    defer_to: binding           # NEW (status=deferred) — only "binding" in v1.1
    deferred_at: <ISO>          # NEW (status=deferred)
    deferred_reason: <text>     # NEW (status=deferred) — optional
    # Out-of-scope status:
    out_of_scope_reason: <text> # NEW (status=out-of-scope)
```

**Backwards compatibility:** OQs without `status` field are treated as `status: pending` by all skills. Existing vault.json files load without conversion.

### 4.3 routing-rules.md update

**Current rule (line 29):**

```
| Vault P0/P1 OQ count > 0 | resolve-oq first (before any other chain) |
```

**New rule:**

```
| Vault has unresolved P0/P1 OQs with status != deferred | resolve-oq first (intent gate) |
| Vault has only deferred P0/P1 OQs + brownfield context | scan-codebase → bind-codebase (auto-resolves deferred) |
```

Deferred OQs **don't block** the intent gate; they propagate to binding phase for code-aware resolution.

## 5. Phase B — Skill Body Updates

### 5.1 resolve-oq SKILL.md (substantive update)

**Currently:** binary resolve/skip per OQ. No `--binding` mode procedure documented.

**New behavior:**

#### 5.1.1 4-action menu per OQ

When resolve-oq walks OQs, each OQ presents:

```
OQ-DATA-001 (P1, section 03-data-model.md)
> "Does the user table have a deleted_at column?"

Choose action:
  [A] Answer now              — provide stakeholder resolution inline
  [B] Defer to binding        — code-dependent OQ; resolve at bind-codebase phase
  [C] Out of scope            — declare irrelevant to current spec
  [D] Skip                    — leave pending, decide later
```

Action **[B]** appears ONLY when:
- Vault `mode: existing` (brownfield) AND
- CWD has repo signals (`.git`, package manifests detected)

Greenfield session OR no-repo context → Option [B] suppressed.

**Per-action state transitions:**

| Action | OQ field changes |
|---|---|
| A — Answer | `status: resolved`, `resolved_at: <now>`, `resolution: <text>` |
| B — Defer to binding | `status: deferred`, `defer_to: binding`, `deferred_at: <now>`, `deferred_reason: <optional>` |
| C — Out of scope | `status: out-of-scope`, `out_of_scope_reason: <text>` |
| D — Skip | (no change) |

#### 5.1.2 `--binding` mode procedure

New top-level section in resolve-oq SKILL.md:

```markdown
## Binding mode (--binding)

Invocation: /mega-sdd:resolve-oq --binding <path-to-binding.md>

Procedure:
1. Load binding.md. Parse Conflicts table (entries with id C-XXX).
2. ALSO parse Open Questions table from binding.md (auto-propagated deferred OQs).
3. Walk each conflict, present 4-action menu per `conflict-resolution.md`:
   - KEEP_VAULT — vault correct; code patch deferred to later
   - KEEP_CODE — patch vault inline to match code
   - DEFER — downgrade CONFLICT to OQ (re-route to next bind iteration)
   - SPLIT — break vault claim into sub-claims; user provides splits
4. Walk OQs from binding.md (same 4-action menu as intent-mode, but Option B hidden because already in binding context).
5. Write resolutions back to:
   - binding.md (Conflicts table updated with resolution column)
   - vault.json changelog (entry: { event: "resolve-oq-binding", at: <iso>, summary })
6. Suggest re-run: `/mega-sdd:bind-codebase` (clean re-binding now that conflicts resolved)
```

### 5.2 bind-codebase SKILL.md (deferred-OQ flow)

**New step 2.5 inserted between current Step 2 (verdict per claim) and Step 3 (aggregate counts):**

```markdown
2.5. Deferred-OQ auto-resolution

   For each OQ in vault with `status: deferred` AND `defer_to: binding`:

   a. Extract OQ text + section context
   b. Search codebase-map for evidence:
      - If OQ mentions a specific entity → search §3 (data models)
      - If OQ mentions an endpoint → search §4 (routes)
      - If OQ mentions a file/symbol → search §2 (public interfaces)
   c. High-confidence match (single unambiguous hit) → auto-resolve:
      - Set OQ status: resolved
      - Add binding.md entry under "Auto-Resolved Deferred OQs" section
      - Cite evidence: vault location + codebase-map location
   d. No match OR ambiguous → propagate to binding.md "Open Questions" section
      (these get walked by user in `/mega-sdd:resolve-oq --binding`)

   Auto-resolve uses fuzzy match with conservative threshold; ambiguity always
   falls back to manual resolution. Never silently auto-resolve a deferred OQ
   that could be wrong.
```

Also: standardize `<vault>-bound/` sibling naming throughout SKILL.md (currently mixed with generic `bound-vault/`).

## 9. Migration & Backwards Compatibility

### 9.1 Vault.json schema

Additive only. Existing OQ entries without `status` field:
- All skills MUST treat absent `status` as `pending`
- `vault.json` writers MAY omit `status` for `pending` OQs (no requirement to write `status: pending` explicitly)
- This minimizes diff churn in vault.json on upgrade

### 9.2 Halt protocol consumers

Existing tools/scripts that parse blocker YAML by `type:` continue to work for the 3 existing types. The 5 new types are additive — consumers learn them as they encounter.

### 9.3 Skill behavior compatibility

resolve-oq's new 4-action menu replaces the old binary menu. No CLI breaking change since both behaviors are interactive. The new "Defer to binding" option is opt-in per OQ — if user never picks it, behavior matches v1.0.

bind-codebase's deferred-OQ auto-resolution is purely additive — vaults without deferred OQs hit the same code path as before.

### 9.4 No file format breaking changes

- vault.json structure unchanged (just new optional OQ fields)
- binding.md structure unchanged (just new optional "Auto-Resolved Deferred OQs" section)
- codebase-map.md format unchanged
- DRIFT-REPORT.md format unchanged (filename was the only fix)
