**Date:** 2026-08-06
**Status:** DRAFT — implementing

Operator mandate: "gue pengen optimasi proses bolts, jadi efisien namun tetap sharp dari sisi kode" + "gue mau remove yg ga perlu juga".
**Moat statement:** no deterministic gate is weakened, delayed, or scoped down. L0 gates, Hard-rule pre/post-flight, acceptance evidence (B4), postflight evidence (B1), whitelist (B3), batch suite (B2) all keep running FULL-HEAD on every attempt, exactly as today. What this spec redistributes is the LLM panel's rounds and the byte-channels between controller and subagents — the judgment tier's shape, never the contract tier's coverage.

## D1 — Attempt rounds: full panel once, verify-and-delta after (replaces full re-panel per attempt)

**Today:** spec ❌ or any Critical → re-dispatch implementer → re-enter at L0 → ALL selected lenses re-run blind over base..new-head. Measured: 2–3 attempts/unit, 4–6 lens dispatches/unit; industry evidence says full re-review per attempt is the churn failure mode (Copilot loop), and fix-guided verification of prior findings is the measured FNR reducer (~55–69% → ~16–29%).

**New round policy (review-panel.md §Attempt rounds):**

- **Round 1 (first attempt): unchanged.** Tier-routed full panel (minimal/standard/full + design), blind, exactly today's protocol.
- **Round 2+ (after a fix re-dispatch): ONE `mega-sdd:resolution-verifier` dispatch replaces the lens re-panel.** It is a read-only agent that receives the ledger path + the open finding IDs, the fix range, and the unit-file path, and performs BOTH halves of the consensus pattern:
  (a) **fix-guided verification** — per open finding: is THIS issue resolved at the new head? Verdict `resolved` requires file:line evidence at the new head; `unresolved`/`regressed` keeps the finding open. The original finding TEXT is judged against the new code — never the implementer's claim of resolution (evidence-gated, Greptile pattern = the B1 recompute doctrine applied to judgment).
  (b) **delta review** — the fix diff plus one hop of dependencies (files the fix diff imports/calls into, when identifiable from the diff), fresh eyes, for NEW issues the fix itself introduced. New findings on files the fix did NOT touch are recorded `advisory` (suppressed from the gate) unless Critical — the anti-churn rule; Critical anywhere still gates.
- **The gate condition is unchanged in strength:** open Critical or spec-❌ finding after the round → re-dispatch within the SAME `--max-retries` budget; budget exhausted with a Critical/spec-❌ still open → `review_critical_unresolved`, verbatim today's halt.
- **Escape hatch — full re-panel instead of the verifier round** when ANY of: the fix range touches > 2 files outside the original findings' files; the fix adds/changes a dependency manifest; the spec lens verdict was ❌ (a misread requirement means the round-1 review itself was against the wrong understanding); the controller states cause (logged in the ledger + bolt-report). Deliberately narrow and logged — the default is the cheap round.
- **Deterministic regression net (why delta is safe):** L0 gates re-run base..new-head on EVERY re-dispatch (unchanged, S7-GATES-2), post-flight Hard rules + acceptance re-run against the new head (unchanged) — regressions outside the delta are the SCRIPTS' job, which is this plugin's standing "gates > rules" doctrine. The panel never was the full-head regression net; pretending it was cost 4–6 dispatches per attempt.
- **Blindness, reasoned (spec-level ruling):** the blind rail's purpose is anti-rubber-stamp for FIRST opinions (§Blind dispatch: no lens sees another's verdict or the self-report before forming its own). The resolution-verifier runs AFTER first opinions exist and its function is to verify their resolution — it sees the findings BY DESIGN and still never sees the implementer's self-report or bolt-report. This is a purpose-scoped application of the rail, same shape as the 2026-07-31 rail rewording precedent, not a weakening: round-1 blindness is untouched, and the verifier cannot rubber-stamp because `resolved` demands new-head evidence per finding.

## D2 — Finding ledger: `<vault>/bolts/U-XXX/findings.json` (stable IDs, evidence-gated resolution)

Controller-written working artifact (Write tool; NOT hook-guarded — it is judgment-tier working state, not gate evidence; the gate inputs remain the evidence artifacts). Created at round-1 merge; updated per round. Schema (versioned `schema: 1`):

```json
{"schema": 1, "unit": "U-003", "attempt": 2,
 "findings": [{"id": "F-1", "lens": "security", "severity": "Critical",
   "file": "apps/api/src/calculation/calculation.service.ts", "line": 118,
   "title": "DTI check fails open on missing income",
   "detail": "<the finding body + WHY, verbatim from the lens>",
   "status": "open|resolved|advisory",
   "resolution": {"attempt": 2, "commit": "<sha>", "evidence": "<file:line + one line>", "verified_by": "resolution-verifier"}}]}
```

Rules: IDs are stable across rounds (never renumbered); **round-1 status mapping** — Critical + spec-❌-implicated findings enter `open`, Important/Minor enter `advisory` (matching the merge gate's severity semantics; the verifier never verifies advisories); `resolved` is written from a resolution-verifier verdict carrying evidence — never from the implementer's report; **escape-hatch rounds close findings via the controller** (round-corrected — the first cut deadlocked: a blind re-panel never references ledger IDs, so nothing could legally close a finding on an escape-hatch round): an open finding whose issue no longer appears in the re-panel's merged results (same file + issue class) is marked `resolved` with `verified_by: "re-panel round N"`; re-reported issues keep their ORIGINAL ids; `advisory` findings surface in `bolt-report.md §Review panel` but do not gate; the ledger is the single source the re-dispatch points at (D3) and the merged table in `bolt-report.md` is derived from it at unit completion AND on any halt (the report keeps its MANDATORY section — the ledger feeds it, not replaces it).

## D3 — Re-dispatch by pointer (kills the growing inline-findings prompt)

**Today:** the merged issue list is inlined into the re-dispatch prompt (measured growth 800B → 9KB per attempt, and one stalled attempt re-paid it in full).
**New:** the fix re-dispatch stays POINTER-SHAPED (never finding bodies): the unchanged base `inline_core` (trace tag, unit id, READ-FIRST pointer to `dispatch-prompt.md`) plus ONE `FIX ROUND — read the finding ledger FIRST:` line carrying the absolute `findings.json` path and the open finding IDs (`F-1,F-4`). The implementer Reads the ledger itself — bodies, reasons, and file:line live there (Cognition requirement: reasons travel, not just verdicts). The controller never re-types findings into the prompt. Same channel discipline as the existing dispatch-file pattern; the dispatch-prompt builder is NOT re-run for a fix round (the unit didn't change — the ledger is the delta).

## D4 — Lens return contract: findings only, no narrative (the 113KB → ~⅓ cut)

Lens agents (spec/quality/security/standards/design reviewers) currently return prose reports (Strengths / Issues / Assessment) measured at 8–15KB each — 4–8× Anthropic's own 1–2k-token subagent return budget, and the narrative is dead weight: the controller's merge consumes ONLY the findings.
**New return contract (each reviewer agent body + review-panel.md):** return EXACTLY a structured findings block — `VERDICT: pass|fail` (spec lens only), then per finding one entry `severity | file:line | title (≤80 chars) | detail (≤3 sentences, must carry the WHY)`, then one `SUMMARY:` line (≤2 sentences). No Strengths section, no Assessment narrative, no restating the unit or the diff. A finding without file:line is dropped at merge (unchanged rule) — so don't emit it. The FULL reasoning stays where it already lives: the lens's own context window, disposable by design (Anthropic context-quarantine pattern). Merge/dedup/consensus/gate logic unchanged.

## D5 — L0 results ride a lens-input file, not 4–5 pasted copies

**Today:** the L0 stdout JSON is pasted verbatim into EVERY lens prompt (`## Deterministic scan results`) — ×4–5 per full-tier attempt, again per re-round.
**New:** the controller writes the L0 JSON ONCE to `<vault>/lens-inputs/U-XXX/l0-results.json` (the directory whose ONLY writer is the controller — same rail as `design-slice.md`) and each lens prompt carries the path + "Read it before judging; machine fact, not another lens's opinion." Re-rounds overwrite the file with the fresh gate output (attempt-1 results must never ride into a re-review — unchanged freshness rule, now enforced by a single overwrite point instead of 4 re-pastes). Blindness intact: the file holds machine output only.

## D6 — Citation churn leaves the inner loop (the "sitasi" ruling)

Research verdict: every measured anti-fabrication win of citations is on the CLAIM side (vault, binding, bolt report, emissions); NO evidence code-side citation strings improve code; even DO-178C validates trace at milestone audits. Field case: a dedicated commit + a full re-verification round to fix `F-C-004`→`F-C-005` in a CODE COMMENT ("comment text only, no behaviour").
**Rulings (bolt-implementer contract + review-panel merge rules):**
- **Code comments do not carry claim/flow/OQ-ID citations.** Trace IDs live in the unit spec and the bolt report — both claim-side, both validated. A comment may describe intent in words; it never cites `F-*`/`C-*`/`OQ-*` (a string that rots into active misinformation — the Mäder/Egyed staleness finding — with zero validated consumer).
- **Non-behavioral citation-string corrections** (in reports, docs, comments predating this rule) are FOLDED into the unit's next substantive commit or its completion evidence commit — never a dedicated fix commit + re-verification round. Logged one-line in the bolt-report.
- **Claim-side citation obligations unchanged:** emit-fsd sha256 stamps, binding anchors, bolt-report source citations, PBT `cites` pre-flight — all exactly as today.

## D7 — Evidence-commit batching (the "remove yg ga perlu" cut)

Measured: separate `chore(sdd): refresh gate state` commits landing 9–19 SECONDS apart, plus per-artifact evidence commits — commit spam that bloats history and the controller's own narration. **New guidance (halts-and-handoff.md §Outputs detail):** when the project versions `.mega-sdd/`, all state-file refreshes + bolt artifacts produced by one unit's attempt cycle are staged into ONE evidence commit at unit completion (`chore(sdd): evidence U-XXX — …`); a standalone gate-state-refresh commit is never emitted. Projects that gitignore `.mega-sdd/` are unaffected. (The bolt's CODE commits are untouched — one atomic code commit per the existing contract.)
