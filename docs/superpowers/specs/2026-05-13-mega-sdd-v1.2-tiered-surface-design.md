## 1. Context & Motivation

### 1.1 Problem statement

User feedback after v1.1.0 ships: "current state too complex, but we want to cover all needs while staying simple and easy to use."

Audit of current complexity sources:
- **11 slash commands** — too many to remember for first-contact users
- **README ~370 lines** — cognitive overload at first read
- **Mode A vs Mode B distinction** in `generate-intent` — requires `--from-prompt` flag for free-text, adds mental tax
- **8 halt types**, **4 OQ statuses + 5 optional fields**, **2 defer types** — semantic richness valuable for AI agents, overwhelming for humans

Categorized as **necessary** (pipeline phases, anti-hallucination layers, architect/dev separation) vs **accidental** (surface presentation, mode flags, doc length).

### 1.2 Design intent

v1.2 attacks **accidental** complexity at the surface layer without touching architectural foundations:

1. **Tiered surface presentation** — Three tiers (primary 3, advanced 8, deep internals) so users encounter complexity progressively based on their need.
2. **Mode auto-detect** — `generate-intent` detects Mode A vs B from positional argument shape; `--from-prompt` flag stays but becomes opt-in.

Out of scope for v1.2 (deferred to v1.3 pending real-usage feedback):
- Collapsing defer types
- Collapsing halt types
- Plugin alias shorthand

## 3. Section 1 — Mode auto-detect for `generate-intent`

### 3.1 Current behavior (v1.1)

```
/mega-sdd:generate-intent ./prd.md            → Mode A (path explicit)
/mega-sdd:generate-intent --from-prompt "..."  → Mode B (free-text)
/mega-sdd:generate-intent                     → smart auto-detect (CWD scan)
```

Flag `--from-prompt` is the mental tax: new users don't know it exists or wonder when to use it.

### 3.2 New behavior (v1.2)

Deterministic detection from positional argument shape:

```
/mega-sdd:generate-intent ./prd.md            → Mode A
/mega-sdd:generate-intent "build a TODO CLI"  → Mode B
/mega-sdd:generate-intent build TODO CLI      → Mode B
/mega-sdd:generate-intent                     → CWD scan (unchanged)
/mega-sdd:generate-intent --from-prompt "..."  → Mode B (explicit override)
```

### 3.3 Detection rules (deterministic, no LLM judgment)

Evaluated in order; first match wins:

| Rule | Match condition | Mode |
|---|---|---|
| 1 | `--from-prompt` flag present | **B** (explicit override; positional ignored as path) |
| 2 | Positional arg resolves to existing file on disk | **A** |
| 3 | Positional arg matches glob `*.md` / `*.pdf` / `*.docx` (whether or not file exists yet) | **A** — but warn if missing |
| 4 | Positional arg contains whitespace OR is wrapped in quotes OR is > 80 chars | **B** (treat as brief) |
| 5 | Positional arg has no path separators (`/`, `\`) AND no recognized extension | **B** |
| 6 | No positional arg | CWD scan: 1 PRD candidate → confirm Mode A; else prompt user |

### 3.4 Edge cases

- **Quoted single word** (`"buildTodoCLI"`) → Mode B per Rule 4 (wrapped in quotes)
- **Bare single word** (`prd`) → Rule 5 matches (no path sep, no extension), Mode B. If user actually wants Mode A, they should provide extension or path: `prd.md` or `./prd`
- **Looks-like-path but doesn't exist** (`./missing.md`) → Rule 2 fails (doesn't resolve); Rule 3 catches the `.md` extension → Mode A with warning "file not found, did you mean to write a brief?"
- **`--from-prompt` + path-looking positional** (`--from-prompt "build X" ./prd.md`) → Rule 1 wins, Mode B; the path is treated as part of the brief or ignored. Document explicitly: when `--from-prompt` is set, positional MUST be the brief text or absent.

### 3.5 Backwards compatibility

All existing invocation patterns continue to work:
- `--from-prompt "..."` — still works, takes precedence
- `./prd.md` — still works
- Empty args — still works

No breaking changes. Auto-detect is purely additive.

### 3.6 SKILL.md update structure

The "Invocation modes" section in `generate-intent/SKILL.md` (added in v1.0) gets:

1. Updated description: "Mode auto-detected from positional argument shape; `--from-prompt` flag remains for explicit override."
2. New "Detection rules" sub-section listing the 6 rules in order
3. New "Edge cases" sub-section listing the 4 cases above

The "Mode A — Structured input" and "Mode B — Free-text brief" sub-sections remain unchanged in their internal procedures.

## 6. Success Criteria

v1.2.0 ships successfully if all of:

1. **Auto-detect works** — Each of the 6 detection rules verified by trigger fixture; no false positives in realistic test cases (paths with spaces, quoted briefs, ambiguous bare strings).
2. **Backwards compat** — Existing v1.0/v1.1 invocation patterns (`./prd.md`, `--from-prompt "..."`, empty) all still work without behavior change.
3. **README first-contact load** — Visible (non-collapsed) content ≤ 150 lines on GitLab/GitHub render.
4. **All info preserved** — Every section from v1.1 README is still findable (just relocated/collapsed); audit reveals zero content deletion.
5. **Version consistency** — `plugin.json`, `marketplace.json`, both READMEs all say 1.2.0; CHANGELOG has v1.2.0 entry.
6. **Trigger test added** — `tests/skill-triggering/generate-intent.test.md` covers auto-detect cases.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Auto-detect false positive (path-looking string treated as Mode A but file missing) | Rule 3 warns user; offers to switch to Mode B; never silently fails |
| Power user confusion: "where did `--from-prompt` go?" | Flag still works; CHANGELOG explicit; SKILL.md says explicit-flag mode for those who want it |
| `<details>` rendering issues on niche markdown viewers | GitLab + GitHub both render natively; falls back to expanded prose on viewers that don't support it (graceful degradation) |
| Content lost during restructure | Self-review checklist (per writing-plans) ensures all v1.1 sections present in v1.2 README, just relocated |
| Trigger phrases hidden in deep-dive collapse become invisible | Acceptable tradeoff — anchor `using-mega-sdd` SKILL.md still has them (that's where it matters for behavior) |

## 9. Open Questions

**OQ-1** Should auto-detect log a one-line "Detected Mode X because rule N matched" hint to the user? Helps debugging false positives but adds noise. **Resolution: Log only when ambiguous** (e.g., Rule 3 matched but file doesn't exist). Confident detections silent.

**OQ-2** When CWD scan finds multiple PRD candidates (Rule 6 ambiguous), should it auto-prompt selection or halt with list? **Resolution: Prompt selection** — same as v1.1 behavior, no change in this case.

**OQ-3** Plugin README is already slim — does it benefit from `<details>` collapses, or is a flat restructure sufficient? **Resolution: Flat** — plugin README is ≤ 60 lines target, doesn't need progressive disclosure.
