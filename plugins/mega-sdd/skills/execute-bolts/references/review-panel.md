# Review Panel — parallel blind reviewer lenses

How the execute-bolts controller reviews a bolt after `bolt-implementer` reports DONE: a risk-tiered panel of read-only lenses dispatched **in parallel, blind**, then merged in the main thread. Design: `docs/superpowers/specs/2026-06-12-review-panel-design.md`.

## The lenses

| Lens | Agent | Model (catalog) | Judges |
|---|---|---|---|
| spec | `mega-sdd:spec-reviewer` | §spec-reviewer | spec fidelity: nothing missing/extra, Hard rules, target_files, acceptance test real |
| quality | `mega-sdd:code-quality-reviewer` | §code-quality-reviewer | duplication/failure-to-reuse, test quality, over-engineering, maintainability |
| security | `mega-sdd:security-reviewer` | §security-reviewer | input validation, authz vs spec, secrets, new deps, fail-open, architectural drift |
| standards | `mega-sdd:standards-reviewer` | §standards-reviewer | naming/location/idiom conformance vs pack + surrounding code |
| design | `mega-sdd:design-reviewer` | §design-reviewer | modern UI quality vs the vault design_system + modern-baseline (UI-bearing units only) |

**Round 2+ verifier (not a lens):** `mega-sdd:resolution-verifier` runs INSTEAD of the lens re-panel on fix rounds — fix-guided verification of each open finding + a delta review of the fix range (+1 dependency hop). See §Attempt rounds below; round-1 dispatch is always the tier-routed lens set above.

**Return-size contract (all lenses + the verifier):** each agent returns a structured findings-only block (`FINDINGS:` rows `severity | file:line | title | detail`, optional one-line `CHECKED-CLEAN:`, `SUMMARY:` ≤2 sentences; the spec lens adds `VERDICT: pass|fail`, the verifier returns `RESOLUTIONS:`+`NEW-FINDINGS:`) — target ≤2k tokens, NO Strengths/Assessment narrative, no restating the unit or diff. The full reasoning stays in the agent's own disposable context; the return is the distilled verdict the merge consumes. A finding row without `file:line` is dropped at merge, so it must not be emitted.

Panel lens models are pinned in each agent's frontmatter (`agents/*-reviewer.md` `model:`) — that is the value the runtime actually uses; the `model-tiers.md` catalog rows document the intended tier, and catalog↔frontmatter parity is a release-time obligation (checked by the panel pin test), not a runtime override. The `model_tiers:` config override chain applies to skill-level model picks, NOT to the panel lenses — a `model_tiers: {security-reviewer: …}` entry is silently ignored at panel dispatch (plugin agents read their own frontmatter).

## Tier selection (risk-based)

Resolve the tier BEFORE dispatch, once per unit:

| Tier | Lenses | Selected when |
|---|---|---|
| `minimal` | spec | (`task_type: verify` with zero signals — signals outrank verify) OR (1–2 declared target files AND zero risk signals; zero DECLARED files on a non-verify unit is unknown scope → `standard`, never minimal) — P3 predicate: the old `no operation: create` clause made this tier near-unreachable; its protection is carried by the six signals + the executed acceptance test + the L0 gates, which run under EVERY tier (the 1 lens sits ON TOP of executed evidence, never instead of it) |
| `standard` | spec + quality | default — anything neither minimal nor full |
| `full` | spec + quality + security + standards | ANY risk signal fires |

**The router is a SCRIPT (P3, rail A5 — deterministic evidence, never model self-assessment).** **Run** `bash <plugin>/scripts/resolve-review-tier.sh --unit <vault>/units/U-XXX.md --pack <resolved-pack-path>` — it evaluates the six signals below mechanically and prints `{"tier", "signals_fired": [...], "signals_evaluated": [...]}`. The controller applies the override chain on top (flag > config > the script's auto verdict); exit ≠ 0 → fall back to `standard` (unknown rc is never a LOW tier). The signal LIST is copied verbatim from this file (plus derived-form stems — authentication/authorization/oauth/menyetujui — the morphology the model era handled implicitly); case-folded glob matching; a frontmatter parse-miss lands `standard` with a `parse_note`, never minimal.

**Additive design lens:** `design-reviewer` JOINS the selected tier (any tier) whenever the unit is UI-bearing per `context-enrichment.md §Design slice` (target_files match the pack `view_glob` or the universal frontend shapes). It receives the SAME design slice as its rubric — one contract, two sides. **The slice arrives as a lens-input FILE** (amended 2026-07-31, round 3; the predecessor carried it as a pasted `design_slice_text` string): `scripts/build-dispatch-prompt.sh` writes the emitted slice verbatim to `<vault>/lens-inputs/U-XXX/design-slice.md` and returns that absolute path in its stdout JSON as **`design_slice_path`** (the file holds the `## Design system (UI-bearing unit…)` section, or on a starterkit repo the `### Starterkit context` design lines). The controller puts the path in the lens prompt; the lens Reads it. **Pure-backend units never pay for it — no file is written and the key is absent, not empty.** That last clause is gated on `ui_bearing`, the same condition that selects this lens: a unit whose `starterkit_relevance` carries `ui_ux` but whose `target_files` are all backend gets **no** lens-input file (round 3 wrote one for it; round 4 closed that). Rationale, the measured double-billing that forced the change, and the fix: `context-enrichment.md §Handing the slice to the design lens`.

> **The blind-review rail, at its purpose: NO lens may receive a path that reaches another lens's verdict or the implementer's self-report.** This is §Blind dispatch below, applied at the mechanism level rather than restated as an intention.
>
> **Applied.** `<vault>/bolts/U-XXX/dispatch-prompt.md` and its directory stay forbidden to every lens: `dispatch-prompt.md` shares a directory with `bolt-report.md`, and on a first attempt that report does not exist yet — so a path would *look* safe — but on `--resume`, on a retry, or on any re-run over a previously-bolted unit the directory already holds the prior attempt's `## Review panel` verdicts and `bolt_self_report`, and a lens with Read/Grep is one `Glob` of the parent directory away from all of it, before forming its own opinion. `<vault>/lens-inputs/U-XXX/` is a SIBLING of `bolts/` and by construction holds **only controller-written lens inputs — never implementer output, never a lens verdict, never a `bolt-report.md`.** That invariant, not the path string, is what makes it safe; a change that starts writing implementer output there breaches the rail without moving a single path.
>
> **This wording REPLACES an absolute form** — *"no path into `<vault>/bolts/U-XXX/`, not the file, not the directory, not a glob that reaches either"* — which §Live-app capture below (unchanged, live, and older than that rule) already violates by routing design-lens screenshots to `<bolt-dir>/views`. A rail the shipping procedure breaches on every UI bolt is not a rail: a reader could not tell which of the two paragraphs to follow, and that ambiguity was the defect. Scoping the rail to its purpose resolves it without weakening it — a screenshot is neither a verdict nor a self-report. The screenshots are nonetheless the named candidate to follow the design slice under `lens-inputs/U-XXX/views/`; see §Live-app capture.

**Live-app capture (the ceiling lens).** The design slice carries `modern-baseline.md §Ceiling moves` — the floor (tokens/states/a11y, provable from code) is not a passing grade; the ceiling (composition, hierarchy, distinctiveness) usually needs the render. Before dispatching the design lens, the controller MAY capture the running app when a dev-server URL is known (`.mega-sdd/config.yaml` `preview_url:` or the operator supplies one — there is NO per-unit frontmatter field; unit-schema.md defines none and generate-units would never round-trip it); captured screenshots are passed to the design lens, which judges the actual render. The capture ladder, top rung first (6.11.0):

1. **Playwright MCP, interactive (the bundled server — when its tools are available).** The CONTROLLER (never the lens — plugin agents cannot carry MCP) drives the page directly and captures **interaction states** the static drivers cannot reach — hover, focus, form-error — plus the breakpoint widths. Files land in the SAME `--out` dir under the naming-contract EXTENSION `<slug>-<state>-<width>.png` (state ∈ `base|hover|focus|error`; the static drivers' `<slug>-<width>.png` is the `base` short form — route+width keying prevents cross-route collisions), and the controller **synthesizes the same JSON** `{"skipped":…,"shots":[{route,state,width,file}]}` record `capture-views.sh` emits — the lens consumes ONE contract regardless of rung.
2. **`scripts/capture-views.sh`** — the static drivers, unchanged: a system Chrome/Chromium first (no Node — works for PHP/Python/Ruby/Go repos), then npx playwright.
3. **Graceful SKIP** — every failure mode (server down, no MCP tools, no headless browser, no URL) degrades to the next rung and finally to a stated SKIP; the lens then judges the ceiling from code and SAYS it saw no render.

**Stack-agnostic** — every rung hits URLs, so it works for any stack (Laravel/Blade, Django, Rails, a Node SPA). Capture is never a gate; an un-captured render is never reported as fine.

> **Named candidate, deliberately NOT changed here (2026-07-31, round 3):** `--out=<bolt-dir>/views` writes controller-produced lens inputs into the same directory that later receives `bolt-report.md`. Those PNGs belong under `<vault>/lens-inputs/U-XXX/views/`, alongside `design-slice.md`, for exactly the reason that put the design slice there — one directory whose only writer is the controller. It is legal today under the purpose-scoped rail above (a screenshot is not a verdict or a self-report) and it is not moved in this change because it touches `capture-views.sh --out` and the procedure that calls it. Carried in `context-enrichment.md §Known open`.

**Risk signals** (evaluate against the unit + active framework pack):
1. Any `target_files` path matches the pack's `auth_hints` or `authz_hints` globs.
2. A dependency manifest (package.json, composer.json, requirements/pyproject, go.mod, Cargo.toml, Gemfile) is in `target_files`.
3. `target_files` count ≥ 4.
4. The unit body mentions auth, session, token, crypto, password, payment, upload — or the authorization class: role, permission, access, admin, acl, approv- (approve/approval) — or the Indonesian equivalents the plugin's ID/EN surface already carries: kata sandi, sandi, pembayaran, unggah, hak akses, peran, izin, otorisasi, autentikasi, persetujuan (all case-insensitive, matched as WHOLE words — `approv-` is the sole deliberate prefix match; a substring inside a longer word never fires: "perancangan"/"perangkat" do not match peran, "accessibility" does not match access — otherwise every a11y-discussing UI unit would pay the full panel). S7-TIER-5: the old EN-only list had NO authz vocabulary and none of the plugin's second language — "Hanya manajer yang bisa menyetujui pengajuan" selected a tier with no security lens.
5. `binding_refs` cite a constitution §B (Security) clause.
6. The unit frontmatter carries `risk: high` or `risk: critical` (the producer-stamped field per `generate-units/references/unit-schema.md`) — this signal ALONE forces `full`; when it disagrees with signals 1–5 (e.g. `risk: critical` on a unit no other signal fires for), log the disagreement in the bolt-report.

**Override chain:** `--review-panel=minimal|standard|full|auto` CLI flag > `.mega-sdd/config.yaml` `review_panel:` > `auto` (the table above). A forced tier is logged in the bolt-report; the `## Review panel` section MUST record `signals_fired[]` beside the tier (the audit trail that makes a low-tier verdict defensible); forcing `minimal` on a unit with risk signals adds a one-line warning (never silent).

## Blind dispatch protocol

- **One message, N Agent calls** — all selected lenses dispatch concurrently from the main-thread controller. Depth-1 is preserved: the controller→agent shape is unchanged; the panel adds parallelism, not nesting.
- **Each lens prompt contains:** base/head commit SHAs + lens-specific context, plus a unit-body slice **sized to the lens**. The **spec lens gets the full unit body verbatim** — it is the lens that verifies Implementation-steps fidelity, Hard-rule honoring, and `target_files` coverage (the moat checks), so it must see everything. The **other lenses (security, standards, quality, design) get frontmatter + requirements + Hard rules + Anchors/Anti-patterns + Migration notes, but NOT the Implementation-steps NARRATIVE** — they judge the landed diff (security judges the actual authz/validation in the code, not the step prose describing it), so the step narrative is dead weight (~40–50% of a typical body) sent 4× per full-tier bolt attempt. **Per-lens orientation-prose trim:** the **security and standards lenses ALSO drop the `## Goal` / `## Context (read first)` / `## Out of scope` prose** from their slice — they judge the landed diff against their own contracts (constitution §B + binding_refs + pack security idioms; pack naming/location/idiom conventions + codebase-map conventions), so the orientation prose is dead weight re-sent per full-tier attempt. The **quality lens KEEPS Goal + Out of scope** (its over-engineering/scope-creep judgment needs the unit's stated intent and its explicit scope boundary) while still dropping Context. The design lens slice is unchanged (orientation prose kept — the design slice is its contract and Goal is its 1-2 sentences of UI intent); the spec lens is untouched (full body verbatim, per above). **Migration notes STAYS in every lens** — on an `extend` unit its KEEP sub-list ("code to preserve, do not touch") is the authoritative preserve-intent for pre-existing controls that predate the unit and are therefore absent from its `binding_refs`/§B slice; the security lens's bypass-detection (a silently-dropped scope filter / middleware) is blind without it, and the list is only a few short lines (near-zero cost). Only the step narrative and the per-lens orientation prose (above) are trimmed — never Hard rules, Anchors/Anti-patterns, or Migration notes. Lens-specific context is unchanged: security gets the constitution §B clauses + binding_refs + the active pack's `## Security idioms` slice; standards gets the pack naming/location/idiom slice + codebase-map conventions; quality gets the reuse-index path + reuse_candidates **+ the mechanical reuse-duplication evidence rows** — the controller runs `scripts/validate-reuse-duplication.sh --cwd=<root> --range=<base>..<head> --json` (one bounded spawn, ADVISORY, rc always 0) and pastes the returned rows under a `## Reuse-duplication evidence (mechanical, advisory)` heading in the quality lens prompt; zero rows → the heading is OMITTED, never emitted empty. On an escape-hatch full re-panel the rows are RE-RUN against the new head exactly like the fresh L0 results — attempt-1 rows must never ride into a re-review (default fix rounds dispatch the verifier, which does not receive the rows — §Attempt rounds). Like the L0 block, the rows are machine fact, not another lens's opinion — blindness is intact; the lens VERIFIES each row (an index match is a lead, not a verdict). Design gets the design slice (vault design_system + style-principles slice + modern-baseline digest).
- **Each lens prompt NEVER contains:** the implementer's report or self-assessment, another lens's verdict, any prior attempt's review, **or any path that reaches one of those** — which specifically forbids `<vault>/bolts/U-XXX/dispatch-prompt.md`, that directory, and any glob reaching either, because the bolt dir holds `bolt-report.md` and a pointer there is the same breach one Read away. **Permitted, because it reaches none of them:** `<vault>/lens-inputs/U-XXX/` — controller-written lens inputs only, never implementer or reviewer output (see the rail above). The design lens's rubric arrives that way, as `design_slice_path`. Everything else a lens needs is pasted as text. Blind review is the anti-rubber-stamp rail — do not "save tokens" by sharing context between lenses, and never route a lens at a directory that also receives implementer or reviewer output.
- **Each lens/verifier prompt ends with a `mega-sdd-trace:execute-bolts` line** — fresh-context subagents never see the session anchor, so the observability tag must ride the dispatch prompt itself (the builder's script-assembled dispatch already stamps it; the controller adds the same line when constructing lens and verifier prompts). One token, verbatim, no variants.
- **Each lens prompt DOES carry the L0 code-gate results — as a FILE path (spec D5)**: the controller writes the L0 stdout JSON ONCE to `<vault>/lens-inputs/U-XXX/l0-results.json` (the directory whose ONLY writer is the controller — same rail as `design-slice.md`) and each lens prompt carries that path + the instruction to Read it before judging. Machine fact, not another lens's opinion, so blindness is intact; the single write point replaces 4–5 verbatim pastes per full-tier attempt. On a re-round the controller OVERWRITES the file with the fresh gate output — attempt-1 results must never ride into a re-review, enforced by one overwrite instead of four re-pastes.
- **Escape-hatch full re-reviews are equally blind** (fix rounds normally dispatch the resolution-verifier instead — §Attempt rounds): the lens gets the new SHAs and the unit, not the history of what it flagged before. The re-review diff range keeps the ORIGINAL bolt base (base..new-head) — the lens judges the whole bolt, never just the fix commit — and `l0-results.json` holds the FRESH L0 results from the re-run gates, never attempt-1 scan output.

## Merge + severity gate

The controller (main thread) merges the lens reports:

1. **Evidence-or-drop** — a finding with no `file:line` anchor is discarded (mirrors the no-fabrication invariant). Log dropped count.
2. **Dedup** — same (file, overlapping lines, same issue class) across lenses → keep one entry at the MAX severity, note all reporting lenses.
3. **Consensus** — a finding reported by ≥2 lenses is marked `confidence: high` in the merged list.
4. **Gate:**
   - spec lens ❌ OR any **Critical** (any lens) → write/update the finding ledger (§Attempt rounds) and re-dispatch `bolt-implementer` **by pointer** — the fix dispatch stays POINTER-SHAPED (never finding bodies): the unchanged base `inline_core` (trace tag, unit id, READ-FIRST pointer to `dispatch-prompt.md`) plus ONE `FIX ROUND — read the finding ledger FIRST:` line carrying the absolute `findings.json` path and the open finding IDs. The implementer Reads the ledger itself (bodies, reasons, file:line live there); the controller never re-types findings into the prompt, and the dispatch-prompt builder is NOT re-run (the unit didn't change — the ledger is the delta). The SHARED `--max-retries` cap applies — panel retries and spec retries draw from the same budget. **A re-dispatch RE-ENTERS the per-unit flow at the L0 code gates** (S7-GATES-2): the gates re-run over **ORIGINAL bolt base..new head**, never fix-commit-only — a fix commit that adds a dependency or pastes a credential must pass `validate-new-deps.sh` / `scan-secrets-code.sh` like any other commit ("always run" means every commit, not every first attempt) — then the fix round is reviewed per §Attempt rounds (resolution-verifier by default; escape-hatch full re-panel when its conditions fire).
   - Retries EXHAUSTED with a Critical still open **OR the spec lens still ❌** → **halt `review_critical_unresolved`** (terminal — the run stops; never proceed to the next bolt over an open Critical or an unmet requirement). Spec ❌ is definitionally must-fix per this gate's own re-dispatch rule — a missing/misread requirement carries no severity grade, so without this clause the exhausted-retries case fell through to "mergeable" (S7-PANEL-4). The halt YAML lives in `references/halt-recovery.md`; the unresolved finding is recorded in `bolt-report.md` `## Review panel`.
   - **Important** findings → recorded in `bolt-report.md` under `## Review panel`; the bolt is mergeable.
   - **Minor** → logged in the same section, no action required.
5. The merged findings are written into `bolt-report.md` `## Review panel` (lens list, tier used, finding table, dropped-no-evidence count) — a MANDATORY section of the canonical schema (`superpowers-bridge.md §bolt-report.md schema`), DERIVED from the finding ledger at unit completion (the ledger feeds the report section, never replaces it).
6. **Citation-string hygiene (spec D6):** a non-behavioral citation-string correction (a wrong `F-*`/`C-*`/`OQ-*` id in a report, doc, or legacy comment — "comment text only, no behaviour") is FOLDED into the unit's next substantive commit or its completion evidence commit, logged one line in the bolt-report — never a dedicated fix commit + re-verification round. (Code comments themselves don't carry claim/flow/OQ-id citations at all — the implementer contract; trace ids live in the unit spec and bolt report, both claim-side and validated.)

The deterministic post-flight Hard-rule scan still runs AFTER the panel passes (both run against the implementer's already-landed commit — detect-after topology per SKILL.md) — the panel is judgment, the scan is the contract. Neither replaces the other.

## Attempt rounds + the finding ledger

Design: `docs/superpowers/specs/2026-08-06-v6.1-bolt-loop-efficiency.md`. The measured churn this replaces: full lens re-panel per attempt (4–6 dispatches/unit, findings re-inlined into growing prompts) — while the industry-consensus round shape is "verify prior findings resolved + delta-review the fix", with the deterministic gates as the full-head regression net.

**The finding ledger** — `<vault>/bolts/U-XXX/findings.json`, controller-written (Write tool) working state (NOT hook-guarded; gate evidence artifacts are unchanged and separate). Created at the round-1 merge, updated every round:

```json
{"schema": 1, "unit": "U-003", "attempt": 2,
 "findings": [{"id": "F-1", "lens": "security", "severity": "Critical",
   "file": "src/calculation/calculation.service.ts", "line": 118,
   "title": "DTI check fails open on missing income",
   "detail": "<finding body + WHY, verbatim from the lens>",
   "status": "open",
   "resolution": null}]}
```

Ledger rules:
- IDs stable across rounds (never renumbered). **Round-1 status mapping:** Critical findings and the findings behind a spec-❌ verdict enter as `open` (these are what fix rounds must close — "the open finding IDs"); Important/Minor findings enter as `advisory` (recorded, surfaced, never gating — matching the §Merge gate's own severity semantics; the verifier is never asked to verify advisories).
- `status: resolved` is written from a **resolution-verifier** `resolved` verdict carrying new-head `file:line` evidence — never from the implementer's report (evidence-gated resolution, the B1-recompute doctrine applied to judgment).
- **Escape-hatch rounds close findings too** (the deadlock guard): when a full re-panel runs instead of the verifier, the CONTROLLER updates the ledger from the fresh merged results — an open finding whose issue no longer appears in the re-panel's merged findings (same file + issue class) is marked `resolved` with `verified_by: "re-panel round N"` and the round's head SHA as evidence; a re-reported issue keeps its ORIGINAL id and stays `open` (never gets a duplicate new id); genuinely new findings get new ids with round-1 status mapping. A clean escape-hatch re-panel therefore closes the round exactly like a clean verifier round.
- `status: advisory` = recorded, surfaced in the bolt-report, does not gate. The ledger-derived `## Review panel` section is written into `bolt-report.md` at unit completion AND on any halt (`review_critical_unresolved` must carry the unresolved finding — the halt path derives the section too, never skips it).

**Round policy:**

- **Round 1** (first attempt): the tier-routed blind lens panel, exactly §Blind dispatch + §Merge above. Unchanged.
- **Round 2+** (after a fix re-dispatch): ONE **`mega-sdd:resolution-verifier`** dispatch replaces the lens re-panel. Its prompt: the UNIT FILE path (`<vault>/units/U-XXX.md` — never `dispatch-prompt.md`; the units dir holds no reports), ORIGINAL base SHA, previous head, new head, `l0-results.json` path (fresh), `findings.json` path + the open finding IDs. **Path scoping (the rail, applied):** `findings.json` is the ONLY file the verifier may read inside `bolts/U-XXX/` — its own contract forbids Glob/ls of that directory and every other file there (`bolt-report.md`, `dispatch-prompt.md`, `partial-state.json` — prior-round verdicts and the implementer self-report live there, and reading them voids the verdict). The verifier (a) verifies each open finding at the new head — `resolved` REQUIRES evidence; `unresolved`/`regressed` stays open — and (b) delta-reviews the fix range + one dependency hop for NEW issues. New non-Critical findings on files the fix didn't touch → `advisory` (the anti-churn rule); a new Critical gates regardless of location. (The mechanical reuse-duplication rows are round-1/escape-hatch quality-lens material only — the verifier's delta review does not receive them.)
- **Gate condition (unchanged in strength):** any finding still `open` at Critical, or the spec-❌ condition unresolved, → next re-dispatch within the same `--max-retries` budget; budget exhausted → **halt `review_critical_unresolved`**, verbatim the §Merge gate rule.
- **Escape hatch — full re-panel instead of the verifier** when ANY of: the fix range touches >2 files outside the original findings' files; the fix adds/changes a dependency manifest; the spec lens verdict was ❌ (the round-1 review judged a misread requirement — re-judge everything); or the controller states cause. The cause is logged in the ledger (a `rounds[]` note) + bolt-report; the escape-hatch re-panel follows the blind re-review rules in §Blind dispatch, and the CONTROLLER maps its merged results back onto the ledger per the escape-hatch ledger rule above (open findings close on non-recurrence evidence; re-reports keep their ids).
- **Why delta is safe (the moat reasoning):** L0 gates re-run base..new-head on EVERY re-dispatch, and post-flight Hard rules + acceptance evidence re-run against the new head — full-head regression coverage is the SCRIPTS' contract, unchanged. The panel is judgment; it never was the regression net.
- **Blindness, purpose-scoped:** the blind rail prevents rubber-stamped FIRST opinions. The verifier runs after first opinions exist and verifies their RESOLUTION — it sees the findings BY DESIGN, and it cannot rubber-stamp because `resolved` demands per-finding new-head evidence. **Reconciling the bolt-dir path grant:** the lens rule ("no path into `bolts/U-XXX/`") exists because a lens is one Glob from verdicts it must not see before forming a FIRST opinion; the verifier necessarily receives ONE named file in that directory (`findings.json` — it cannot live under `lens-inputs/`, whose invariant is "never a lens verdict") and is contract-bound to read nothing else there (no Glob, no `bolt-report.md`, no `dispatch-prompt.md`). This is the same purpose-scoped application of the rail as the screenshots ruling above — the prohibition plus the named-file scope is the rail; round-1 blindness is untouched.

## Cost notes

A full panel is ~4 fresh agent contexts on the FIRST attempt — multiples of a single-reviewer run; fix rounds pay ONE verifier context instead (§Attempt rounds). The tier table is the round-1 cost control: routine bolts pay for one lens, risky bolts pay for four. Tune per project via `review_panel:` in `.mega-sdd/config.yaml` (e.g., `full` for a payments service, `standard` for an internal tool). Per-lens models are frontmatter-pinned and NOT tunable via `model_tiers:` (see the pin note above).
