## 1. Pack-resolver call sites swallow non-zero exits

**Source:** `skills/execute-bolts/references/context-enrichment.md` §Known open, row 1. That file was deleted in P3 C5, together with `scripts/build-dispatch-prompt.sh`.

**What is wrong.** Every surviving caller of `scripts/_lib/resolve-framework-pack.sh` has the form `X=$(bash "$PACK_RESOLVER" … ) || X=""`. There are 11 call sites in 4 validators, counted at the P3 C5 commit:
- `validate-flow-coverage.sh`: 4
- `validate-sibling-consistency.sh`: 4, including the `--fanout-parity` and `--cross-cutting` modes
- `validate-ui-quality.sh`: 2, including `--deferral`
- `validate-unit-spec.sh`: 1

On Windows, `python3` can resolve to the App-Execution-Alias stub (exit 49; see `scripts/_lib/resolve-python.sh`). The resolver then fails, and the caller cannot tell that failure from a project with no pack. Those gates go quiet and exit 0. Some of them block at PreToolUse.

**Correction to the old row.** The row said that the builder and `validate-dispatch-prompt.sh` honoured the exit-code contract. The builder did. `validate-dispatch-prompt.sh:117` did not: it swallowed the exit code like the others, so there were 12 call sites. Both scripts were deleted in P3 C5. No surviving caller honours the contract now.

**The contract to implement** (it was in the deleted file under §Pack-resolver exit codes):
- Capture the resolver's exit code. Do not replace a failure with an empty chain.
- Exit 0: use the chain. Exit 3: the documented skip; no pack applies.
- Any other exit: the chain is unknown, not empty. Record a warning that names the exit code and the interpreter used. A packless project and a failed resolver must never read the same.
- Pass an interpreter that is already resolved (`MEGA_SDD_PY`) to the resolver, so a stub `python3` on `PATH` cannot decide the outcome.

**Why it was not fixed in P3.** The problem predates P3. It spans four scripts, including PreToolUse-blocking gates, and needs Windows portability tests. P3 only deletes code.
