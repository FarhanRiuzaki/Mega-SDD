## 2d. Amendemen #4 — stale line-range anchor: auto-repair bersyarat hash-identik (SHIPPED 7.38.0)

Kelas P2 (klinik U-008 `.env.example:1-29` pada file 28 baris; xs U-006): range anchor melewati EOF satu baris → CONFLICT nyata di JIT bind → controller resolve KEEP_CODE + betulkan anchor sendiri (±10 menit per unit; xs 7.37.0 ±10 m di BOLT-1). | Rule | Syarat (semua harus terpenuhi) | Hasil |
|---|---|---|
| **R1-shift** | snapshot penulisan anchor (commit yang memperkenalkan token itu ke file unit; token yang baru ada di working tree = file saat ini) memuat range → blok baris itu ditemukan **verbatim dan unik** di offset lain pada file saat ini | CONFIRMED, anchor digeser, `repair {from,to,rule:R1-shift,reference,content_sha256}` |
| **R2-clamp** | file saat ini **byte-identik** dengan snapshot DAN range melewati EOF **tepat satu baris** (salah hitung newline penutup = kelas P2) | CONFIRMED, dijepit ke EOF, `repair {…rule:R2-clamp…}` |
| tetap CONFLICT | konten berubah / match tidak unik / overshoot > 1 / tidak ada snapshot | seperti sebelumnya (`resolve-oq --binding`) |

Baris `## Anchors` unit ditulis ulang ke token hasil repair (atomik, hanya token itu), `repairs[]` dicatat di `binding.json`, stdout writer memuat `repaired`/`repairs`. Range yang masih muat **tidak disentuh** (memperketatnya = perubahan rate CONFLICT yang harus diukur dulu). `[ASSUMED-BY-RUNNER]`: R2 dibatasi overshoot = 1 supaya range halusinasi (mis. `1-40` pada file 28 baris) tidak "diperbaiki" diam-diam — batas ini persis kelas yang terukur di P2, bukan angka ajaib.
